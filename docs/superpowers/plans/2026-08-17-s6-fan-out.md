# s6 fan-out (approach C) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Split s6's single model call into one call per category so its one corrective retry is spent on the failure that actually kills it, without changing s6's persisted shape, its renderers, or `report.yaml`.

**Architecture:** A third opt-in table `FAN_OUT` in `lib/ai/sections.ts` declares, per section, how to enumerate units, how to narrow the section slice to one unit, and how to merge units back. `gateSection` and `sliceCategoryIds` gain an **optional** `GateUnit` parameter that swaps the registry slice and the length ceiling for the unit's. `composeReport` stops mapping `AI_SECTION_IDS` and maps a derived `CallUnit[]`; both rounds operate on units, a failing unit retries alone, and a fanned section is stored only if **every** unit succeeded.

**Tech Stack:** TypeScript (strict), Zod v4, OpenAI `responses.parse`, vitest. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-08-17-s6-fan-out-design.md` (commit `833821d`). The spec is the authority. Where this plan and the spec disagree, **escalate** — do not reconcile silently. Where this plan and the **source** disagree, **source governs**: fix the plan, note it in the task's commit message, and carry on.

## Escalation E1 — CLOSED (Natalie, 2026-08-17). Task 3 is unblocked.

Spec §3.5 requires that attempt 1's prompt "additionally states the budget **per beat** rather than only per section", and §8 R2 names that per-beat prompt as half the bet that 1200 chars/area is enough. Spec §3.1 fixes `FanOutEntry` at exactly three fields (`keys`, `slice`, `merge`), none of which carries a beat count, and the beat count cannot be re-derived inside `lib/ai/sections.ts` without importing `COVERAGE_FIELD` from `lib/ai/section-gates.ts` — which already imports `sections.ts`, so that is an import cycle.

**Proposed resolution (the default this plan is written against):** add a fourth field `beats: number` to `FanOutEntry` (`s6: 6`), and an optional second parameter to `budgetSentence`. Both are shown in full in Task 1 Step 3 and Task 3 Step 3.

**Alternatives, if the fourth field is unwanted:** (a) drop the per-beat clause entirely — the change still ships, but §8 R2's bet loses half its mechanism and R2 becomes more likely; (b) put the beat count in `SECTION_REGISTRY` instead, which widens an interface all seven sections share for one section's benefit.

**RULING (Natalie, 2026-08-17): the proposed resolution, as written.** A fourth field `beats: number` on `FanOutEntry` (`s6: 6`, a LITERAL) plus an optional second parameter on `budgetSentence`. Rationale on the record: `FanOutEntry` is brand-new, opt-in and single-consumer, so widening it costs nothing outside the fan-out, whereas alternative (b) would widen a contract all seven sections share for one section's benefit; and alternative (a) would drop the per-beat clause that spec §8 R2 names as half the bet that 1200 chars/area is enough — the measured failure is a model writing to the beat count rather than to the ceiling. `beats` stays a literal rather than a schema-derived expression **on purpose**: Task 1's assertion `expect(FAN_OUT.s6!.beats).toBe(beatFields.length)` is then a real drift tripwire (`e497c40` doubled s6's beats 3 -> 6 and left `report.yaml` stale — that drift is the origin of this whole problem), where a derived value would make the same assertion tautological.

```ts
/**
 * Fan-out: the sections whose ONE model call is split into several, one per unit.
 *
 * A third opt-in table beside SECTION_REGISTRY, in the same `Partial<Record<AiSectionId, …>>`
 * idiom COVERAGE_FIELD and STRUCTURAL_NUMBERS use in section-gates.ts: an entry opts a section
 * in, absence is today's single-call behaviour. **s6 only.** s5 has the same array shape and
 * could be added later without redesign, but nothing has measured a problem there — do not add
 * it speculatively.
 *
 * WHY s6 and not the others (design doc §1): gateSection returns on the FIRST failure and
 * composeReport allows exactly ONE re-attempt, so s6's single corrective is ALWAYS spent on
 * `category coverage`; attempt 2 clears coverage and dies on `length ceiling` with no attempt
 * left. The measured length corrective has never once been issued for s6. One call per category
 * makes coverage unfailable (one id, one entry) and hands the retry to the failure that
 * actually kills the section.
 */
export interface FanOutEntry {
  /** The unit keys, read off the SECTION slice — never by re-deriving `.slice(3)` here. */
  keys: (facts: FactsPack) => readonly string[];
  /** One unit's slice: the section slice with ONLY `categories` narrowed (design §3.2). */
  slice: (facts: FactsPack, key: string) => unknown;
  /** Units back to the section's persisted shape. */
  merge: (parts: readonly unknown[]) => unknown;
  /** Prose beats one unit must fill, for the per-beat budget sentence (design §3.5). */
  beats: number;
}

export const FAN_OUT: Partial<Record<AiSectionId, FanOutEntry>> = {
  s6: {
    keys: (f) => (SECTION_REGISTRY.s6.slice(f) as { categories: CategoryFact[] }).categories.map((c) => c.id),
    // Defined by SUBTRACTION from the section slice, not by copying it: head, blind_spots,
    // dispersion, top_three, bottom_items and growth_trajectory keep exactly one source and
    // cannot drift from SECTION_REGISTRY.s6.slice. Only `categories` narrows. A key matching
    // nothing yields an empty array, which fails closed at gate 1b.
    slice: (f, key) => {
      const base = SECTION_REGISTRY.s6.slice(f) as { categories: CategoryFact[] };
      return { ...base, categories: base.categories.filter((c) => c.id === key) };
    },
    // No new schema: a unit reuses S6Schema and returns `{ areas: [ one ] }`. Because each part
    // was already gated — parity-checked against S6Schema, coverage-checked to exactly its own
    // id — the merged whole satisfies S6Schema by construction and carries exactly one entry per
    // key, in `keys` order.
    merge: (parts) => ({ areas: parts.flatMap((p) => (p as { areas: unknown[] }).areas) }),
    beats: 6,
  },
};
```
